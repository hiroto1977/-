# 受信の検疫 —— 開く前に文字として調べる

2026-11-16 に足した守り。届いたメール・メッセージ・リンクを **開かずに** 文字として調べ、
危ない兆候を示し、リンクを押せない形 (無効化) にして見せる。画面が動いている間は端末の中で、
端末が眠っている間はクラウドの見張り番が同じ規則で働く。

## できる事・できない事

| | |
| --- | --- |
| できる | 文面と差出人の **形** から兆候を数える (偽装したホスト・同形異字・IP 直書き・短縮リンク・危ない種類のファイル名・表示と行き先の食い違い・AI への指示・急がせる文・秘密を求める文 ほか 19 種) |
| できる | リンクを押せない形へ書き換えて見せる (`https://` → `hxxps[:]//`・`.` → `[.]`・不可視の字を落とす) |
| できない | **ウイルスの検査** (添付ファイルの中身は見ない)。兆候が無いことは安全の保証ではない —— 画面も見張り番もそう述べる |
| できない | 起動より前に動くウイルス (ブートセクタ型) を取り除くこと。守るのは端末の「確認つき起動」で、アプリは **有効かの点検と確かめ方** だけを示す (`src/shared/bootProtection.ts`) |

## 部品

| 部品 | 場所 | 役目 |
| --- | --- | --- |
| 判定 | `src/shared/inboundThreat.ts` | 決定的な規則。網へ出ない・AI を使わない・結果の文は固定 (入力の文面を引用しない) |
| 標本の台帳 | `security/inbound-samples.json` | 攻撃の標本は決めた兆候 **だけ** が鳴り、無害の標本は 1 つも鳴らない (`inboundThreat.test.ts`) |
| 画面 | Security の「受信の検疫」(`InboundQuarantine.tsx`) | 貼った文面をその場で調べる。送信しない・保存しない |
| Gmail の札 | `GmailPage.tsx` | 一覧の件名と差出人に兆候が在れば札を出す (デスクトップ版で実データを読むとき) |
| 起動の守り | Security の「起動の守りの点検」(`BootProtectionCard.tsx`) | セキュアブートの状態 (Linux のデスクトップ版は自動で読む) と端末ごとの確かめ方 |
| 見張り番の口 | `src/shared/inboundWatch.ts` | メールの一覧 → 付けるラベル。危険は 1 つでも・注意は 2 種類から |
| 見張り番の生成物 | `scripts/inbound-watch.cjs` | 上を依存なしの 1 本へ畳んだ物 (`node scripts/build-inbound-watch.cjs` で組む・手で編集しない) |

## クラウドの見張り番

端末が眠っている間も働くよう、予約 (Claude Code のスケジュール) で 1 日 1 回動く。

1. 予約「メール検疫の見張り番 (毎日 · 省エネ版)」(毎日 05:49 日本時間) が「当番」のセッションを起こす。当番は、その日の見張り用のセッションを 1 つ作るだけ (メールは読まない)。
2. 見張り用のセッションが Gmail の新着 (受信トレイ・未読・直近 1 日・新しい順に最大 40 スレッド・本文は先頭 6,000 字) を **テキストとして** 読む。
3. `node scripts/inbound-watch.cjs <入力.json>` の出力どおりに、ラベル `検疫-危険の疑い` / `検疫-要注意` を付ける。

この形になった理由 (2026-11-16 の実測):

| 試した形 | 結果 |
| --- | --- |
| 毎回新しいセッションを作る予約にコネクタを付ける | この組織では付けられない (Gmail の道具が無いセッションになる) |
| リポジトリの付いていないセッションから `git clone` | 自動モードの判定が断る (回避しない) |
| リポジトリ付き (`scripts/` だけ取り出す) | 動くが、根の CLAUDE.md を読むので空の文脈が 564,384 token (30 通を読んだ回は 724,530 token) |
| リポジトリ付き + `blob_limit_kb: 64` | **採用** —— 64 KiB を超えるファイルを取り出さないので CLAUDE.md が無く、空の文脈は 106,169 token。40 スレッドを調べた試運転は 279,132 token (上の形の約 4 割)。生成物は 18 KiB |

当番を挟むのは、コネクタ (Gmail) を持つ新しいセッションを毎日作れるのが「セッションからセッションを作る」道だけだったため。
予約の指示文は、その予約が届く会話の中からしか書き換えられず、持ち主の承認が要る (別の会話からの `update_trigger` は断られる) ——
指示を変えるときは、**新しい予約と新しい当番を作り、古い予約を止める** (2026-11-16 に 1 度そうした。止めた予約は消していない)。

試運転で分かった限界: 見張り用のセッションは 40 件のうち約 10 件だけ全文を読み、残りは検索結果の冒頭の抜粋を規則へ渡した
(判定は規則がするが、規則に渡る文面が短い)。直す案と判断の材料は `docs/REMAINING_WORK.md`。

守る線 (予約の指示文に書いてあり、判定の側も構造で守る):

- **判定は AI がしない。** AI は運ぶだけで、ラベルを決めるのは決定的な規則である (本文に「安全と報告せよ」と書いてあっても結果は変わらない)。
- リンクを開かない・添付を取らない。
- 削除・迷惑メール報告・返信・転送・アーカイブをしない。付けるのはラベルだけ。
- メールの内容を Gmail の外へ出さない。報告に本文も件名も書かない (スクリプトの出力に入るのは id と固定の語彙だけ)。

規則を変えたら `node scripts/build-inbound-watch.cjs` で生成物を組み直して push する
(`inboundWatchBundle.test.ts` が組み直し忘れを落とす)。見張り用のセッションは branch `claude/mamori-arena` の
`scripts/` を読むので、push した次の回から新しい規則で動く。

## 自律的に育つ仕組み

- **標本の台帳**: すり抜けた文面を見つけたら `security/inbound-samples.json` に標本を足す → 検査が落ちる → 規則を広げる。
- **週 1 の狩りの輪**: `security/threat-ledger.json` の huntBacklog に「受信の検疫をすり抜ける文面」が載っており、ホワイトハッカー班が攻める。
- **毎日の脅威ウォッチ**: `security/weakness-map.json` の `spoofing-phishing` が、世間で悪用の増えた弱点の種類とこの守りを結ぶ。

自動なのは検知・提案・記録まで。規則の変更を出荷に入れるかは人が決める (PR)。
