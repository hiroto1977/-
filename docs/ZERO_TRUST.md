# ゼロトラストの設計 — 「侵入させない」ではなく「動くたびに確かめ、被害を止める」

最終更新: 2026-10-21 (パス 546・脅威 T-147 / T-148 / T-155)

## 0. 先に正直に

**「どんな攻撃者も侵入できない」を保証するシステムは存在しない。** ゼロデイは定義上、まだ誰も知らない欠陥であり、
知らない物を事前に塞ぐことはできない。だから目標を次のように置き直す。

1. **侵入の確率を下げる** (入口を減らす・既知の穴を塞ぐ・供給網を固定する)。
2. **侵入されても、動くたびに止める** (信用を持ち越さない・毎回、画面とは独立の経路で人に確かめる)。
3. **止まった事実から学ぶ** (断られた回数で自動で締まる・見つけた穴は台帳と検査に変わる)。
4. **できないことを書く** (下の「保証しないこと」)。

## 1. 脅威のモデル (誰が・どこから)

| 攻撃者 | 到達点 | 主な手口 |
| --- | --- | --- |
| 画面を操る者 (XSS・取り込んだ文書に仕込まれた指示に従う UI エージェント・悪意の拡張) | レンダラーの JS | `window.serviceHub` を正しい引数で呼ぶ。画面側の確認 (`window.confirm`) は自分で押せる |
| 複数の AI エージェントが同時に攻撃 | 上記を並列・高速に | 速度で人の確認を押し流す・確認ダイアログを連打して疲れさせる・内容を少しずつ差し替える |
| 供給網 (依存・CI・指示書) | ビルド・開発者の端末 | 依存の乗っ取り・workflow の注入・指示書への命令文の混入 |
| 外部サービスの応答 | 読み取り結果 | 反射された秘密・巨大な応答・指示の密輸 (不可視文字) |
| OS 全体を操る者 | OS | ネイティブのダイアログも押せる (**この文書の範囲外**) |

## 2. 層 (深さのある防御)

| 層 | 何をするか | 実体 |
| --- | --- | --- |
| 入口を減らす | 外向きの待受は 127.0.0.1 の OAuth 受け 1 つだけ。file:// は dist/ に閉じ込める | `fileRequestGate.ts` (T-140) |
| 信用しない入力 | 外から来る文は全部データ。不可視文字・端末制御文字・巨大本文を落とす | `lint:charset`・`redact.ts`・`httpLimits.ts` (T-133/134) |
| **毎回の本人確認 (新・T-147)** | 資格情報の書き換え・削除・全削除・外部への書き込みは、**主プロセスのネイティブ確認**を通らなければ実行しない。書く内容を見せる。既定は「実行しない」 | `userPresence.ts`・`presenceWiring.ts` |
| 呼び出し元の検査 | 同梱 dist の最上位フレームだけを信用する | `isTrustedSenderUrl` |
| 適応する締め | 断られるほど締まる (10 分に 3 回→ロックアウト 5 分、続くたびに倍・上限 1 時間)。確認が開いている間の次の要求は断る。段階ごとの速度制限 | `createPresenceGate` |
| 最小権限 | 全 action に段階 (`ACTION_TIER`)。台帳に無い action は最も厳しい扱い | `userPresenceCensus.test.ts` |
| **出力インターセプター (新・T-215)** | 端末の外へ出る段階 (external-write / egress) の本文に資格情報・マイナンバー・カード番号の形が在れば、**本人確認より前に規則で断る** (AI が「送れ」と判断しても送る側が止める)。断りは欄の場所と種類だけを言い、値は引用しない。両ビルドが同じ 1 つを呼ぶ | `outboundContentGate.ts`・`actionTier.ts` |
| **入力の無害化 (新・T-216)** | 第三者の文 (Gmail / Slack の本文・SKILL.md) に混ざった AI への指示の形 (役割の乗っ取り / 指示の上書き / 隠蔽・漏洩の指示 / 区切りの偽装) を、**AI へ届く前・鍵を読む前**に規則で止める。利用者自身が打つ文は検めない | `promptInjection.ts` (emotions / skills / web-shim) |
| **AI の応答は手足を動かさない (新・T-217)** | AI の応答を受ける束縛は外向きの `invoke` / `openExternal` / `fetch` / `window.open` の引数に現れない (今日 0 件を census で固定) | `aiReplyInert.test.ts` |
| **起動時の自己検算 (新・T-218)** | 梱包版は窓を作る前に同梱した全ファイルの sha256 をビルドが書いた表と突き合わせ、1 byte でも違えば起動しない (**読めない = 通さない**)。Linux では fuse の asar integrity が何も照合しないのでこれが唯一の段 —— 容器ごと差し替える相手は表も書き換えられる (署名の無い Linux の限界) | `selfAttestation.ts`・`build-integrity-manifest.cjs`・`smoke:packaged` |
| 費用の暴走 | 1 回の送信回数・同時 1 つ・1 時間 12 回 | `bestAnswersJob.ts` (T-146) |
| 改竄検知 | 守りの実体と、それを守る検査・設定を整合性チェーンと CODEOWNERS で覆う | `integrity-chain.cjs`・`CODEOWNERS` |
| 供給網 | release の検査/署名の分離・workflow の構造門・依存の台帳 | T-142〜T-145 |

### 2.1 「動こうとする度に本人確認」の実装範囲

確認の対象 (毎回・承認は再利用しない): `secrets:set` と `oauth:authorize` (自分のクライアント ID のとき) (credential-write)・
`secrets:clear` と `app:eraseAll` と `emotions/clear-history` (destructive)・
外部へ書き込む `create-/send-/sync-/purge-` 系 20 action と `security/scan-url` (external-write)。
`app:openExternal` は確認を出さず速度だけ制限する。
確認しない (速度のみ): 外部 AI へ送る egress 13・端末内の local-write 15・read 5。**全部に確認を付けると承認の疲れで
「はい」が反射になり、守りが逆に弱くなる** ため、被害が外へ出る・戻せない操作に絞った。

### 2.2 警戒態勢 — 瞬時に締まる層 (T-155)

「外から穴を開ける」「瞬間移動のように侵入する」手口は、実際には**手探りの試行**(信頼できない呼び出し元・
速度超過・確認の割り込み・`file://` の手探り・遷移の試行)の連続として主プロセスに観測される。門はこれらを
**警戒の元**として数え、5 分間に 6 件に届くと**自動で警戒へ入る**(人の判断を待たない):

| | 平常 | 警戒 |
| --- | --- | --- |
| 確かめる段階 | destructive / credential-write / external-write | `read` 以外の全段階 (egress・local-write も毎回) |
| 速度の上限 | 段階ごとの値 | 1/4 (最低 1) |
| ダイアログ | 通常 | 「警戒態勢」を告げる |
| 戻り方 | — | 警戒の元が途絶えて 10 分で自動 (勢いが続く間は延びる) |

止めはしない (誤検知が可用性の事故にならないように、**摩擦を増やして攻撃の速度を人の速さへ落とす**)。
感知器は 2 つが外から知らせる: `file://` の門が断った要求 (T-140)・窓の遷移の門が止めた遷移。記録は種類と
短い場所の名前だけで、URL や値の中身は運ばない。

## 2.9 確率に依らない守り —— 王冠の宝石 (2026-10-23 · T-169)

「侵入される確率が極めて低い」は守りを省く根拠にしない。攻撃は AI で速く多くなり、確率の見積もりは当たらない。
代わりに、**破られたときに失う物**で守りを決める。`security/crown-jewels.json` に守る物を 5 つ置く
(資格情報・主プロセスの実行・配布の供給網・事業データ・秘密の出口)。物ごとに次の 4 層を、**別々の強制物**で持つ。

| 層 | 問い |
| --- | --- |
| 防ぐ (prevent) | 入口を塞ぐ |
| 封じ込める (contain) | 防ぎが破れても、被害をその物の中に止める (防ぐと強制物を共有しない) |
| 気付く (detect) | 破られたことが見える |
| 戻す (recover) | 破られた後に元へ戻せる |

`scripts/crown-jewels.cjs` (`npm run audit:crown-jewels`) が、層の欠け・強制物の不在・
別々の強制物が 3 個未満・防ぐと封じ込めの共有・確率で諦める言い回しを落とす。毎日の dependency-audit が同じ測定を常設 Issue に載せる。
**できないこと**: 10^-29 % を証明する仕組みではない。強制物が『在る』ことは確かめるが『十分に強い』ことは確かめない (それは狩りと回帰検査の仕事)。

## 3. 保証しないこと

- **OS 全体を操る攻撃者** (OS 上の画面操作エージェント・マルウェア) はネイティブのダイアログも押せる。
- **ブラウザ版 (単一 HTML)** には主プロセスが無く、この門は届かない。唯一の門は保管庫の解錠とマスターパスワード。
- **承認の疲れ**: 正当な操作で何度も訊かれると反射的に承認する。対策は対象を絞ること・書く内容を見せること・同じ内容の再試行だけを 30 秒まとめること。
- **「瞬時の解析と対策」の範囲**: 瞬時に働くのは**既知の型の手探りに対する自動の締め付け**だけ (上の警戒態勢)。未知の手口を実行中に解析して新しい防御コードを自分で書き足す仕組みは**作っていない** —— 実行中の自己書き換えは、乗っ取られたときに最悪の足場になるため意図して置かない。新しい手口を規則に変えるのは、赤青の周回 (人が確かめ、検査で留める) が担う。
- **ゼロデイ**: 未知の欠陥は塞げない。被害の上限を決めておく (確認・速度制限・費用の窓) ことで、悪用されても外へ出る量を小さくする。

## 4. 進化し続ける仕組み

**攻撃側と防御側のラウンド制** (`docs/RED_BLUE.md`): 独立した監査役が破りに行き、私が再現して確かめ、本物だけを直して対照実験で留める。ラウンド 1 では本人確認の門に対し 9 件が見つかり、7 件を直した (T-148)。

1. **見つけたら台帳に書く** — `security/threat-ledger.json` (T-番号・再現・直し・回帰検査)。
2. **直したら対照で確かめる** — 守りを壊し、狙った検査だけが落ちることを見る。鳴らない対照は「検査についての報せ」。
3. **母集団を数える** — 新しい IPC・action が足されたら census が名指しで落ちる (台帳に段階を書かせる)。
4. **変異検査で守りの検査を測る** — `userPresence.ts` は `mutate` の対象 (break 99.8)。
5. **定期点検** — `npm run audit:*` (毎日の依存監査・SHA 固定の実在確認・脅威ウォッチ (悪用中の弱点と守りの突き合わせ · T-164) ほか)。
6. **適応は実行時にも** — ロックアウトの伸びと警戒態勢は、観測した事実から自動で決まる (2.2)。
