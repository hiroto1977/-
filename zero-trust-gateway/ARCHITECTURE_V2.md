# ARCHITECTURE_V2 — 自律進化型 6 層ゼロトラスト (Autonomous 6-Layer Zero-Trust)

この文書は、自社の Linux サーバーで動かす API を守るための設計書です。
Claude Code に渡して、この順に実装を進められる形で書いています。

- 版: 2.0 (設計。どこまで作ったかは [`README.md`](README.md) の表 —— 2026-11-21 の時点で第 3・4・5・6 層と、第 1 層の一部)
- 言語: Python 3.12 以上 (FastAPI / Pydantic v2 / `cryptography` / `webauthn`)・Bash・nftables
- 守る物: 自社の API と、そこから出る短命トークン・監査記録

## 0. 先に読む — この設計が「できる事」と「できない事」

元の案には、そのままでは成り立たない所がいくつか在ります。実装の前に直しておきます。

| 元の案の言い方 | 実際 | この設計での扱い |
| --- | --- | --- |
| 「API キーを廃止する (キーレス化)」 | 廃止できるのは**自社の API** の鍵だけ。外部サービス (他社の API) は、相手が鍵を要求する限り鍵が残る | 自社 API は DPoP の短命トークンへ。外部の鍵は金庫 (Vault) に置き、コードと設定ファイルに書かない |
| 「盗まれても別端末では使えない」 | トークンは端末の秘密鍵に結び付くので、**トークンだけ**盗んでも使えない。端末ごと乗っ取られたら使える | 第 3 層 (人の確認) と第 4 層 (ふるまいの監視) で補う |
| 「メモリから秘密鍵を読むのは物理的に不可能」(TEE) | TEE は読み取りを大幅に難しくするが、「不可能」ではない (サイドチャネルの報告が在る)。使える機械も限られる | 第 2 層は後の段階。無い環境でも他の 5 層は動く形にする |
| 「Bluetooth の近接を自作で検証」 | 自作は危ない。パスキーの「別の端末で認証」(hybrid transport) が、QR と Bluetooth で近接を確かめる仕組みを既に持つ | 自作しない。WebAuthn の標準の動きを使う |
| 「Tailscale または fwknop (SPA)」 | Tailscale は SPA ではない。ただし土台の WireGuard は、鍵を持たない相手に一切応答しないので、外からは閉じて見える | どちらか 1 つを選ぶ (§3.1) |
| 「耐量子 TLS (X25519MLKEM768)」 | TLS ライブラリの版に依る (OpenSSL 3.5 以上・Go 1.24 以上が目安)。構築の時に版を確かめる | 使える版なら有効にし、使えない相手には従来の X25519 で応じる |
| 「AI が異常を判定して即座に凍結」 | AI だけに決めさせると、誤判定で正しい利用者を締め出す。ログには攻撃者が書いた文も混ざる | 止める判断は決まった規則。AI は点数の補助と説明だけ |
| 「攻撃者を自動で反撃」 | 相手の機械へ手を出すのは違法になりうる | するのは**自分の側の遮断と隔離だけ** |
| 「WORM (書き換え不能) 監査」 | 同じサーバーの中だけでは、管理者権限を取られたら消せる | ハッシュの鎖 + 鎖の先頭を**別の場所**へ定期的に控える |
| ディレクトリ名 `layer2_zkp_attest` | ゼロ知識証明 (ZKP) は使っていない。中身は端末の証明 (attestation) | 名前は指定どおり残すが、文書では「証明」と呼ぶ |

**この設計が約束しない事**: 「絶対に破られない」とは言いません。層を重ねて、1 つ破られても次で止まる・気付ける・戻せる形を目指します。

## 1. 守りの規則 (全層に共通・必ず守る)

1. **秘密を書かない (Zero Hardcoded Secrets)** — パスワード・鍵・トークンをコードにも設定ファイルにも書かない。起動時に生成するか、環境変数で受ける。リポジトリに置くのは値が空の `.env.example` だけ。検査用の鍵は検査の中で毎回作る。
2. **層を分ける (Modular)** — 各層は `src/layerN_*/` に置き、他の層の中身を直接読まない。層の間は §4 の型だけでやり取りする。
3. **まず安全側 (Safety First)** — ファイアウォール (`nftables`) と停止スイッチに触る物は、**既定が `--dry-run`** (何をするかを刷るだけ)。実際に動かすには `--execute` を付ける。開発中に自分を締め出さないため。
4. **検査を付ける (Testing)** — 各層に `pytest` の単体検査と結合検査を `tests/` に置く。
5. **迷ったら断る (Fail Closed)** — 検証に失敗した・読めない・時間切れは、すべて「通さない」。ただし遮断の側 (第 6 層) は逆で、**迷ったら遮断しない** (誤って自分を締め出さない)。
6. **遮断は時間で切れる** — 自動の遮断は必ず期限つき (nftables の `timeout`)。永久の遮断は人が決める。
7. **締め出されない道を残す (Break-glass)** — 管理用の IP の一覧と loopback は、どの自動遮断でも対象にしない。
8. **ログに秘密を出さない** — トークン・鍵・証明の本体は記録しない。記録するのは指紋 (SHA-256 の先頭) だけ。
9. **外から来た文はデータ** — ログ・リクエスト・ヘッダの文を AI に渡すときは、指示ではなくデータとして渡す。AI の出力から直接、遮断・発行・削除を起こさない。
10. **攻めの検査は自分の中だけ** — 自動の攻撃役 (§3.4) は、隔離した場所で自分のアプリだけを相手にする。外の機械・本番には向けない。

## 2. 全体の流れ

```
利用者の端末                         自社サーバー (Linux)
────────────                         ───────────────────────────────────────────
① ノック 1 パケット ───────────────▶ [第1層] 入口は全部閉じている。正しいノックの間だけ
                                              その IP に 443 を開ける (30 秒)
② TLS (耐量子ハイブリッド) ────────▶ [第1層] リバースプロキシ (Caddy / Nginx)
③ 端末の証明 ──────────────────────▶ [第2層] 端末が改ざんされていないかを確かめる (後の段階)
④ 物理キー + スマホの生体 ─────────▶ [第3層] WebAuthn。2 つの別々の認証器
⑤ トークンをください (DPoP) ───────▶ [第5層] 端末の鍵に結び付いた 5 分のトークンを出す
⑥ API を呼ぶ (毎回署名) ───────────▶ [第5層] 署名とトークンを毎回確かめる
        ▲                            [第4層] ふるまいに点数を付ける → 高ければ追加の確認 / 凍結
        │                            [第6層] おとりに触れたら遮断・すべてを鎖つきで記録
        └──── 追加の確認の要求 ◀──────
```

## 3. 層ごとの仕様

### 3.1 第 1 層 — 見えない入口と耐量子通信 (`src/layer1_mtd/`)

**目的**: ポートスキャンに何も返さない。通信を保存されて将来解読される攻撃 (HNDL) に備える。

**入口は 2 通りから 1 つ選ぶ**

| 案 | 向く場面 | 中身 |
| --- | --- | --- |
| A. WireGuard (または Tailscale) | 利用者が決まっている・少人数 | 鍵を持たない相手に応答しない。運用が軽い。**推奨** |
| B. SPA (単一パケット認証) | 不特定の場所から、VPN なしでつなぐ | 下の `knockd` か、既製の `fwknop` |

**B を選んだときの設計 (`knockd`)**

- UDP のポート 1 つで待つ。**何も返信しない**。
- ノックの中身 (AEAD: ChaCha20-Poly1305 で封じる): `client_id` / `timestamp` / `nonce` (16 バイト以上の乱数) / `want_port`
- 検証: ① 復号できる ② 時刻が ±30 秒以内 ③ `nonce` を見たことが無い (5 分の控えと照合) ④ `client_id` が登録済み
- 通ったら: `nft add element inet spa allowed { <送信元 IP> timeout 30s }` (既定は dry-run で、この行を刷るだけ)
- 鍵は利用者ごとに 1 つ。サーバーは起動時に環境変数から読む。
- 既知の限界: 送信元 IP は NAT の外側の IP になる (同じ NAT の内側の人にも 30 秒開く)。だから第 1 層だけに頼らない。

**nftables の骨組み (`deploy/nftables/spa.nft`)**

```
table inet spa {
  set allowed   { type ipv4_addr; flags timeout; }
  set blocked   { type ipv4_addr; flags timeout; }
  set admin     { type ipv4_addr; }            # 締め出されない道 (規則 7)
  chain input {
    type filter hook input priority 0; policy drop;
    iif lo accept
    ct state established,related accept
    ip saddr @admin tcp dport 22 accept
    ip saddr @blocked drop
    udp dport $KNOCK_PORT accept               # ノックは受けるが返信しない
    ip saddr @allowed tcp dport 443 accept
  }
}
```

**耐量子 TLS**: プロキシの鍵交換に `X25519MLKEM768` を先頭、`X25519` を次に置く (Nginx + OpenSSL 3.5 以上なら `ssl_ecdh_curve X25519MLKEM768:X25519;`。Caddy は Go 1.24 以上で既定)。TLS 1.3 のみ。**構築の時に、実際にその群で握手できたかを確かめる** (`openssl s_client -groups X25519MLKEM768`)。

**モジュール**

| ファイル | 役目 |
| --- | --- |
| `knock_packet.py` | ノックの組み立てと検証 (純粋な関数・網に触らない) |
| `replay_cache.py` | `nonce` の控え (期限つき) |
| `firewall.py` | nft の命令を**組み立てる**だけ。実行は `runner.py` |
| `runner.py` | `--dry-run` (既定) なら刷る・`--execute` なら実行。IP は `ipaddress` で検めてから |
| `knockd.py` | UDP の待ち受け |

**検査**: 時刻のずれ・同じ `nonce` の 2 度目・壊れた封・未登録の `client_id` をすべて断る / dry-run では子プロセスを 1 度も起こさない / IP でない文字列は命令に入らない / `admin` の IP は遮断の命令に入らない。

**機械が要るか**: 検証と命令の組み立ては要らない (検査できる)。実際に開け閉めするには Linux サーバーと root が要る。

### 3.2 第 2 層 — 端末とサーバーの証明 (`src/layer2_zkp_attest/`)

**目的**: 乗っ取られた端末からの操作を通さない。サーバーの中の鍵を OS から隠す。

- **端末の側**: TPM 2.0 の「引用 (quote)」を検証する。サーバーが出した使い捨ての値 (nonce) に対して、端末の TPM が起動時の測定値 (PCR) に署名して返す。サーバーは ① 署名の鎖 (EK 証明書 → AK) ② nonce が一致 ③ PCR が許可した値の一覧に在る、を確かめる。
  - 既製の道具: Keylime (Linux の遠隔証明)。自作するのは検証の規則だけ。
  - Apple の端末は TPM ではない (Secure Enclave)。端末管理 (MDM) の証明を使う。**対応する端末の種類を先に決める**。
- **サーバーの側**: 機密 VM (AMD SEV-SNP / Intel TDX) の証明書を起動時に取り、鍵の払い出しの条件にする。**使える機械かクラウドでしか動かない**。
- **無い場合の動き**: `ATTESTATION_MODE=off | report | enforce`。`off` でも他の層は動く。`report` は記録だけ、`enforce` は通さない。

**モジュール**: `challenge.py` (nonce の発行と期限) / `tpm_quote.py` (引用の検証) / `policy.py` (許可する PCR の一覧) / `tee_report.py` (機密 VM の証明の検証・後回し)。

**検査**: 古い nonce・別の nonce・許可に無い PCR・鎖が切れた署名を断る (検査用の鍵は検査の中で作る)。

**機械が要るか**: 検証の規則は要らない。本物の証明を取るには TPM つきの端末 / 機密 VM が要る。**最後の段階**。

### 3.3 第 3 層 — 物理キーと生体の二重確認 (`src/layer3_fido2/`)

**目的**: 遠隔のなりすまし・キー 1 本の盗難・別の場所に居る人の承認を防ぐ。

- 規格は WebAuthn (FIDO2)。ライブラリは `webauthn` (py_webauthn)。
- **2 つの別々の認証器**を要求する:
  1. 物理キー (YubiKey ほか): タッチ + PIN (`userVerification: required`)
  2. スマホのパスキー: 顔 / 指紋。PC からは「別の端末で認証」(hybrid) を使う —— QR と Bluetooth で**近くに居ること**を規格が確かめる (自作しない)
- 2 つの確認が **120 秒以内**にそろったときだけ「強い認証済み」とする。
- 登録できる物理キーは機種の一覧 (AAGUID) で絞る (`attestation: direct`)。
- 保存するのは公開鍵・認証器の ID・署名カウンタだけ。**秘密は端末から出ない**。
- 署名カウンタが戻ったら (複製の疑い)、その認証器を止めて第 6 層へ知らせる。
- 強い認証済みの状態は 12 時間まで。危ない操作 (停止スイッチ・認証器の追加) の前には、もう一度確認する。

**エンドポイント**

| 道 | 役目 |
| --- | --- |
| `POST /auth/webauthn/register/options` ・ `/register/verify` | 認証器の登録 (既に強い認証済みの人だけ) |
| `POST /auth/webauthn/authenticate/options` ・ `/authenticate/verify` | 確認 |
| `GET /auth/session` | いまの認証の強さ (`none` / `single` / `strong`) |

**検査**: 別の challenge・別の origin・利用者確認なし (UV=false)・戻ったカウンタ・一覧に無い機種・同じ認証器 2 回での「二重確認」を断る。

**作るときに決めた事 (2026-11-21)**

- **認証の状態は、端末の鍵 (DPoP の鍵の指紋) に結び付ける。** クッキーや合言葉を配らない。第 3 層の道はどれも DPoP の証明が要り、
  同じ鍵の証明を出せた相手だけが「強い認証済み」として `/token` に通る。
- **確認は、利用者の名前を聞かない** (認証器が持つパスキーから選ばせる)。名前の当て推量に、何も答えない。
- **最初の 1 台は、1 回きりの登録コードで登録する。** 認証器を足せるのは強い認証済みの人だけなので、最初には別の入口が要る。
  管理者が道具 (`python -m layer3_fido2.enrollment new`) でコードを作り、本人へ別の道で渡す。保存するのはハッシュだけ・期限は 15 分・
  足せるのは、その人がまだ持っていない種類だけ。
- **2 つの種類は、鍵の性質で分ける。** 物理キーは「端末に閉じた鍵 + 発行元の証明書へつながる証明 + 一覧に在る機種」、
  スマホは「同期されるパスキー」。同じ物理キーを 2 つの種類として登録して、1 本で二重確認に見せる形を断る。
- **機種の一覧と発行元の証明書のどちらかが空なら、物理キーは 1 本も登録させない** (機種を名乗っているだけの鍵を受けない)。
- **1 回の確認は、1 組にしか数えない。** 2 つがそろった時点で使い切る —— 追加の確認を、片方の押し直しだけで済ませない。
- **署名カウンタは、署名を確かめた後に比べる** (署名の無いごみで、他人の認証器を止めさせない)。
- **認証器を足す道は、発行を止めている間と、重くしたセッション (追加の確認待ち・凍結) では閉じる** (登録コードを除く)。
- **利用者が押す画面 (`GET /auth/`) は、秘密を持たない静的な 1 枚** (2026-11-21 · 後から足した)。端末の鍵は画面が WebCrypto で
  取り出せない形に作り、その端末 (IndexedDB) にだけ置く。外の物を読まず、CSP は中身のハッシュだけを許し、通信は同じオリジンだけ・
  cookie を送らない・転送に追いかけない。許可 (トークン) はメモリにだけ置いて画面に出さない。道の名前は画面からの相対で書き、
  `PUBLIC_BASE_URL` に道の前置きが在っても同じ文で動く。

**機械が要るか**: 検証の規則は要らない (検査用の認証器をソフトで作る)。実際に使うには物理キーとスマホが要る。

### 3.4 第 4 層 — ふるまいの監視と、攻め役・守り役の検査 (`src/layer4_ai_evolution/`)

**目的**: 認証を通った後の乗っ取りに気付く。守りを検査で育てる。

**(a) ふるまいの点数 (UEBA)**

- 入力 (1 リクエストごとの出来事): 時刻・道・結果・送信元の国と回線・端末の指紋・トークンの指紋
- 点数 (0〜1) は**決まった規則の足し算**が土台:
  - いつもと違う国 / 回線 +0.3 ・ いつもと違う時間帯 +0.1 ・ 1 分あたりの要求数がその人の普段の 5 倍超 +0.3
  - 短時間に失敗が続く +0.2 ・ 触ったことの無い道への連続アクセス +0.2 ・ 同じトークンが 2 つの IP から +0.5
- 統計の補助: その人の過去 30 日の中央値からの外れ具合。AI (ローカル LLM) は**点数の理由を人に説明する文を作るだけ**。
- 動き: 0.6 以上 → 追加の確認 (第 3 層をもう一度) / 0.85 以上 → そのセッションを凍結し、管理者の承認を待つ
- **AI の出力では止めない** (規則 9)。止めるのは上の数だけ。
- キーの打ち方・マウスの軌跡は**個人のデータ**なので、既定では集めない (集めるなら本人の同意と、保存期間の定めを先に)。

**(b) 攻め役と守り役 (Red / Blue)**

- 攻め役 (`red_runner.py`): 隔離した場所で、**自分のアプリをプロセスの中で**叩く (網へ出ない)。道具は性質ベースの検査 (Hypothesis) と、API の形からの入力生成 (schemathesis)。見るのは「断るべき入力を通していないか」「500 を返していないか」「秘密が応答に出ていないか」。
- 守り役 (`blue_proposer.py`): 攻め役が見つけた入力を回帰検査として `tests/regression/` に足し、規則の直しを**提案 (差分) として出す**。本番へは自動で入れない —— 人が読んで入れる。
- 攻め役は、外の機械・本番・他人のサービスへ向けない (規則 10)。攻撃コードを作る道具にしない。

**モジュール**: `events.py` / `baseline.py` / `scoring.py` / `actions.py` / `explain.py` (AI・任意) / `red_runner.py` / `blue_proposer.py`。

**検査**: 各規則が点数を正しく足す / しきい値ちょうどの動き / 履歴が無い人を「異常」にしない / AI が落ちていても点数は出る / AI の出力に「凍結せよ」と書いてあっても何も起きない。

**機械が要るか**: 要らない。

### 3.5 第 5 層 — 鍵の文字列を持たない認可 (`src/layer5_ephemeral/`)

**目的**: 漏れたら終わりの「長く生きる鍵」を無くす。

**人と端末 → DPoP (RFC 9449)**

- 端末は鍵の組を作る (ブラウザなら取り出せない鍵・CLI なら TPM か物理キーの中の鍵が望ましい)。
- トークンをもらうとき・API を呼ぶときは**毎回**、証明 (DPoP proof) を付ける:
  - ヘッダ: `typ: dpop+jwt` ・ `alg` (ES256 か EdDSA だけ。`none` と共通鍵方式は断る) ・ `jwk` (公開鍵)
  - 中身: `jti` (使い捨ての番号) ・ `htm` (メソッド) ・ `htu` (URL) ・ `iat` (時刻) ・ `ath` (トークンのハッシュ)
- サーバーの検証 (1 つでも外れたら 401):
  1. 署名が `jwk` で通る  2. `typ` と `alg` が許可の中  3. `htm` / `htu` がこの要求と一致
  4. `iat` が ±60 秒以内  5. `jti` を見たことが無い  6. `ath` がトークンのハッシュと一致
  7. トークンの `cnf.jkt` (鍵の指紋) が `jwk` の指紋と一致
- トークン: 署名つき JWT・**寿命は 300 秒以下**・更新トークンは出さない (切れたらもう一度証明して取り直す)。
- トークンを出す条件: 第 3 層が `strong` ・ 第 4 層の点数が 0.6 未満 ・ (あれば) 第 2 層が通っている。

**サービスどうし → SPIFFE / SPIRE**: 人が居ないやり取りは、SPIRE が配る短命の証明書 (1 時間以下) で相互 TLS。

**外部サービスの鍵**: 無くせない。金庫 (HashiCorp Vault ほか) に置き、使う処理にだけ・使う間だけ渡す。コード・設定・ログに出さない。

**使い捨ての作業場**: 危ない処理は 1 回ごとのコンテナで動かし、終わったら捨てる (root なし・書き込み不可・既定で網なし)。

**サーバーの署名鍵**: 起動時に作るか金庫から受ける。**24 時間ごとに替える** (前の鍵は、出したトークンが切れるまでの 5 分だけ検証に残す)。

**エンドポイント**: `POST /token` / `GET /.well-known/jwks.json` / 守られた道はすべて `Authorization: DPoP <token>` と `DPoP: <proof>` を要求する。

**検査**: 上の 7 つを 1 つずつ外して断ることを確かめる / 300 秒を 1 秒でも超えたトークンを断る / 別の鍵で作った証明では盗んだトークンが使えない / 同じ `jti` の 2 度目を断る / 鍵を替えた後、古い鍵のトークンは 5 分で通らなくなる。

**機械が要るか**: 要らない (**最初に作れる**)。

### 3.6 第 6 層 — 自動の遮断・隔離と、消せない記録 (`src/layer6_soar/`)

**目的**: 未知の攻撃・内部の証拠隠しに備える。被害を広げない。

**(a) おとりの鍵 (canary)**

- 配備の時に乱数で作る。保存するのはハッシュだけ。**どの権限も持たない**。コードに書かない (規則 1)。
- 誰かが使ったら: ① 記録 ② その IP を期限つきで遮断 (既定 24 時間・dry-run が既定) ③ 同じ人のセッションをすべて切る ④ 通知
- 自分を締め出さない歯止め: `admin` の IP と loopback は遮断しない / 1 分に 20 件を超える遮断は止めて人を呼ぶ (送信元を偽った嫌がらせへの備え)。

**(b) 対応の手順書 (playbook)**

| 出来事 | 自動でする事 | 人がする事 |
| --- | --- | --- |
| おとりに触れた | 遮断 (期限つき)・セッション切断・通知 | 原因の確認・遮断の延長 / 解除 |
| 点数 0.85 以上 | セッション凍結 | 承認 / 却下 |
| 署名カウンタが戻った | その認証器を停止 | 本人確認と再登録 |
| 証明に失敗 (enforce) | その端末を拒否 | 端末の調査 |
| 記録の鎖が合わない | トークンの発行を止める | 調査 (停止スイッチの段 1) |

**(c) 消せない記録 (監査)**

- 1 行 1 件の追記だけのファイル。各行は `前の行のハッシュ` を含み、`hash = SHA-256(前のハッシュ + 正規化した中身)`。
- 鎖の先頭 (最新のハッシュ) を**別の場所**へ定期的に控える (別のサーバー / 書き換え禁止を設定した保管先 / 紙)。これが在って初めて「後から消されたら分かる」。
- `audit verify` で鎖を最初から検算する。合わなければ (b) の最後の行。
- 記録に秘密を入れない (規則 8)。

**(d) 停止スイッチ (kill-switch)**

| 段 | する事 | 既定 |
| --- | --- | --- |
| 1 | トークンの発行を止める (出した分は 5 分で切れる) | dry-run |
| 2 | 外向きの入口を閉じる (`admin` の SSH だけ残す) | dry-run |
| 3 | 物理の遮断 (GPIO のリレー / Webhook) | **無効で出荷**。配線と手順が決まってから |

実行には `--execute` と、第 3 層のもう一度の確認が要る。**戻し方 (`--restore`) を同じ道具が持つ**。

**(e) 作り直し**: 侵害の疑いが在るコンテナは、調査用の写しを取ってから捨て、署名を確かめたイメージから作り直す。

**モジュール**: `canary.py` / `playbooks.py` / `blocklist.py` (第 1 層の `runner.py` を通す) / `audit_log.py` / `audit_anchor.py` / `killswitch.py` / `notify.py`。

**検査**: おとりの照合は時間が一定の比べ方 / `admin` と loopback は遮断の命令に入らない / 1 分 20 件で止まる / dry-run では何も実行しない / 記録の 1 文字を変えると検算が落ちる・行を抜いても落ちる / 停止スイッチは `--execute` なしで何も変えない / `--restore` で元に戻る。

**機械が要るか**: 記録・おとり・命令の組み立ては要らない。実際の遮断は Linux サーバーが要る。

## 7. 受け入れの検査 (層をまたぐ流れ・`tests/integration/`)

1. 正しい利用者: ノック → 二重確認 → トークン → API 成功 → 記録に 4 行。
2. トークンだけ盗んだ相手: 別の鍵の証明では 401。記録に `denied`。
3. 6 分前のトークン: 401。
4. 同じ証明の使い回し: 2 度目は 401。
5. おとりの鍵: 遮断の命令が (dry-run で) 刷られ、セッションが切れ、通知が出る。`admin` の IP なら遮断の命令は出ない。
6. 点数 0.6: 追加の確認を求める。0.85: 凍結し、承認までトークンが出ない。
7. 記録を 1 行書き換える: `audit verify` が落ち、トークンの発行が止まる。
8. 停止スイッチ: `--execute` なしでは何も変わらない。
9. リポジトリ全体に秘密らしい文字列が無い (`gitleaks`)。

## 8. 運用で決めておく事 (コードでは決まらない)

- 物理キーは 1 人 2 本 (予備)。無くしたときの手順。
- 締め出されたときの入り方 (`admin` の IP・サーバーの手元の画面)。**紙に書いて保管**。
- 記録の先頭の控え先と、控える間隔 (例: 1 時間)。
- 遮断の解除を誰が決めるか。夜間の通知を誰が受けるか。
- 行動の記録を取るなら、本人への説明と保存期間。
- 半年に 1 度、停止スイッチと復帰を試験用のサーバーで練習する。

## 9. 残る危険 (正直に)

- 端末そのものを乗っ取られ、本人が物理キーに触れてしまう場合 (だまされて承認する)。→ 危ない操作の前の再確認と、第 4 層で減らす。無くせない。
- 管理者権限を取られた後の、サーバーの中の記録。→ 外の控えで「消されたこと」は分かるが、止められない。
- 自動の遮断が、正しい利用者を巻き込む (同じ NAT・同じ VPN)。→ 期限つきにして減らす。
- 依存する部品 (ライブラリ・OS) の弱点。→ `pip-audit` と更新の習慣。
- 耐量子の方式そのものが将来破られる可能性。→ 従来の方式と重ねる (ハイブリッド) ので、片方が残れば守られる。
