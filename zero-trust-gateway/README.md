# zero-trust-gateway — 自社の API を守る 6 層の入口 (作りかけ)

自社の Linux サーバーで動かす API の前に置く、6 層の守りの部品です。
設計は [`ARCHITECTURE_V2.md`](ARCHITECTURE_V2.md) に在ります。

**サービスハブ (このリポジトリの本体のアプリ) とは別の物です。** 本体の画面にも、配る HTML にも入りません。
置き場所だけを借りています。

## いま在る物・まだ無い物

| 層 | 中身 | 状態 |
| --- | --- | --- |
| 第 1 層 入口 | nftables の命令の組み立て・既定が dry-run の実行役・ルールの骨組み | **一部** (ノックの検証と待ち受けはまだ) |
| 第 2 層 端末の証明 | 守りのソフト (EDR・端末管理) が署名した**端末の健康の証明**の検証・感染の知らせ (`/device-health/alerts`) による隔離 | **一部** (健康の証明と隔離は在る。TPM / 機密 VM の証明はまだ —— 機械が要る) |
| 第 3 層 物理キーと生体 | WebAuthn の検証 (登録・確認)・2 つの認証器が 120 秒以内にそろったら「強い認証」・1 回きりの登録コード・利用者が押す画面 (`/auth/`) | **在る** (実物の物理キーとスマホでは、まだ試していない) |
| 第 4 層 ふるまいの点数 | 6 つの規則の点数・追加の確認 / 凍結・説明の文 | **在る** |
| 第 5 層 鍵を持たない認可 | DPoP の証明・5 分のトークン・署名鍵の入れ替え | **在る** |
| 第 6 層 遮断と記録 | おとりの鍵・遮断の計画・対応の手順・鎖つきの記録・停止スイッチ | **在る** (知らせの送り先・記録の外への控えはまだ) |

**本番ではまだ使えません。** 既定のままでは、トークンを 1 枚も出しません —— 認証器が 1 つも登録されておらず、
登録コードの置き場 (`ENROLLMENT_FILE`) も、物理キーの機種の一覧と発行元の証明書 (`ALLOWED_AAGUIDS` / `ATTESTATION_ROOTS_FILE`) も空だからです。
これは意図した動きです。第 3 層は検査用のソフトの認証器と、ブラウザの試験用の認証器でしか確かめていません。

## 強い認証までの流れ (第 3 層)

どの道も DPoP の証明 (端末の鍵の署名) が要ります。認証の状態はその鍵に結び付き、クッキーや合言葉は配りません。

1. 管理者が登録コードを作り、本人へ別の道 (対面など) で渡す (下の「道具」)。
2. 本人が、物理キーとスマホのパスキーを 1 つずつ登録する (`POST /auth/webauthn/register/options` → `/register/verify`)。
3. 2 つで確認する (`POST /auth/webauthn/authenticate/options` → `/authenticate/verify` を 2 回)。**120 秒以内にそろったら**強い認証。
4. `POST /token` でトークンをもらう (5 分)。強い認証は 12 時間で切れる。

| 断る物 | 理由 |
| --- | --- |
| 片方だけ・同じ種類を 2 回・120 秒を超えてあいた 2 つ | 「2 つの別々の認証器」になっていない |
| 利用者確認 (PIN・生体) の無い応答・別のサイト・別の乱数・使い回し | WebAuthn の決まり |
| 証明書の無い物理キー・一覧に無い機種・設定していない発行元 | 機種を名乗っているだけで、確かめようが無い |
| 同期されないスマホの鍵・物理キーの機種を「スマホ」として登録 | 同じ物理キー 1 本で二重確認に見せる形を防ぐ |
| 署名カウンタが戻った認証器 | 複製の疑い。その認証器を止めて、知らせる |

## 利用者が押す画面 (第 3 層)

`<PUBLIC_BASE_URL>/auth/` を開くと、登録と確認をする 1 枚の画面が出ます (日本語・スマホ幅で使える)。

- **この端末の鍵** —— 画面は WebCrypto で鍵を作り、取り出せない形でこの端末 (IndexedDB) にだけ置きます。
  要求のたびにその鍵で DPoP の証明を付けるので、確認の結果はこの端末の鍵に結び付きます。画面の「この端末の鍵を消す」で消せます
  (登録した認証器は消えません)。
- **外の物を読まない** —— スクリプトと見た目は 1 枚の HTML に入っていて、CSP は中身のハッシュだけを許します。
  通信は同じオリジンだけで、cookie を送らず、転送 (リダイレクト) に追いかけません。ほかのページの枠には入れません。
- **許可は画面に出さない** —— 「許可をもらって試す」は 5 分の許可をメモリにだけ置き、守られた道を 1 回通して結果だけを出します。
- 画面は誰でも開けます (秘密を持たない)。守っているのは、画面が叩く入口の道のほうです。

## 感染した端末・アカウントを通さない (第 2 層)

入口は、相手の端末がウイルスに感染しているかを**自分では見られません**。見られるのは端末の中の守りのソフト
(EDR・端末管理 MDM) だけです。そこで、守りのソフトの管理サービスが端末ごとに署名して出す**健康の証明**を、
トークンを出す**前に**検めます (`src/layer2_zkp_attest/`)。

1. **トークンを求める要求に、健康の証明を付ける** (`Device-Health` ヘッダ)。証明は署名つき (ES256 / EdDSA) で、
   発行元の鍵は `DEVICE_HEALTH_ISSUERS_FILE` に置いた公開鍵だけを信頼する。
2. 次の全部が成り立つときだけ「健康」:
   本人 (`sub`) と端末の鍵 (`cnf.jkt` = DPoP の鍵) が要求と同じ ・ 出してから 10 分以内 ・ 動いているウイルスが無い ・
   未解決の脅威が 0 ・ 守りのソフトが動いていて改ざんされていない ・ 定義ファイルが 72 時間以内 ・ OS の更新が 45 日以内 ・
   ディスクの暗号化とファイアウォールが有効。欄が欠ける・型が違う証明は通さない。
3. **感染を報せた証明が来たら隔離する** —— その利用者と端末を隔離の控え (`QUARANTINE_FILE`) に入れ、
   その端末で使われていた端末の鍵を退役させ、その人のセッションを止め、人に知らせる。
4. **守りのソフトからの知らせ** (`POST /device-health/alerts`、`{"alert": "<署名つきの知らせ>"}`) —— 「感染した」で
   その瞬間から隔離し (期限内のトークンも通さない)、「片付いた」で隔離を解く。知らせは署名・宛先・時刻・
   使い捨ての番号 (`jti`) を検め、同じ知らせの 2 度目は断る。
5. **隔離はモードに依らず効く** (`ATTESTATION_MODE=off` でも、署名つきの知らせは止める)。健康の証明を要求するかは
   モードで決める: `report` は記録だけ、`enforce` は証明が無い・通らない端末にトークンを出さない。
6. 隔離を解いても、**感染していた端末の鍵は使わせない**。利用者は「この端末の鍵を消す」で新しい鍵を作り、強い認証からやり直す。

**約束しない事**: 守りのソフトそのものが乗っ取られて嘘の証明を出すと、ここでは見分けられません。
端末の起動の測定値まで確かめる形 (TPM の証明) は後の段階です。

## 守っている規則

1. **秘密を書かない** — 鍵・トークン・パスワードをコードにも設定にも書かない。署名鍵は起動時にメモリで作り、
   おとりの鍵は道具が乱数で作って、保存するのはハッシュだけ。検査 (`tests/test_settings_and_secrets.py`) が全ファイルを見る。
2. **層を分ける** — 層は `src/layerN_*/` に分け、やり取りは `src/contracts.py` の型だけ。
3. **まず安全側** — ファイアウォールと停止スイッチは、既定が dry-run (何をするかを刷るだけ)。
   動かすのは `FIREWALL_EXECUTE=true` / `--execute` を明示したときだけ。遮断は必ず期限つきで、管理用の IP と自分自身は遮断しない。
4. **検査を付ける** — `tests/` に層ごとの検査・層をまたぐ流れ・性質の検査。

## 検査の動かし方

```
python3.12 -m venv .venv
.venv/bin/pip install --require-hashes -r requirements.txt
.venv/bin/python -m pytest
```

リポジトリの CI (`.github/workflows/ci.yml`) も同じ手順で回します。

第 3 層の画面 (`/auth/`) は、本物のブラウザ (Chromium) でも通します。入口を手元の 127.0.0.1 だけで起こし
(`tests/browser/serve.py` —— 試しの登録コード・登録済みの鍵・発行元の証明書はその場で作り、終わったら消す)、
画面のボタンを利用者と同じ順に押して、画面の文と状態を確かめます。

```
# playwright (と Chromium) が要る。リポジトリの直下で:
ZT_PYTHON=zero-trust-gateway/.venv/bin/python node zero-trust-gateway/tests/browser/auth_page.cjs
```

CI では `.github/workflows/gateway-browser.yml` が、`zero-trust-gateway/` を触ったときだけ同じものを回します
(Chromium を落とすので、毎回は走らせない)。この検査が画面のボタンを全部押すこと・秘密を刷らないこと・入口に抜け道を作らないことは、
`tests/layer3/test_l3_browser_harness.py` が pytest で見ます。

依存は `requirements.txt` に版とハッシュで固定しています (一覧の形は `npm run lint:deps` の規則 12 が見て、毎日の弱点チェックが OSV へ照会します)。足すときは `requirements.in` を書き換えて、
`uv pip compile requirements.in --generate-hashes --python-version 3.12 -o requirements.txt` で作り直します。

## 道具

```
# おとりの鍵を 1 つ作る (鍵は 1 度だけ表示・控えるのはハッシュ)
PYTHONPATH=src python -m layer6_soar.canary new

# 記録の鎖を検算する (控えた件数とハッシュを渡すと、末尾の切り落としも見つかる)
PYTHONPATH=src python -m layer6_soar.audit_log verify /var/lib/zt/audit.jsonl

# 最初の認証器を登録するための、1 回きりの登録コードを作る (コードは 1 度だけ表示・15 分で切れる・ファイルに残るのはハッシュ)
PYTHONPATH=src python -m layer3_fido2.enrollment new --subject alice --file /var/lib/zt/enroll.jsonl

# 停止スイッチ (既定は dry-run)
ISSUANCE_HALT_FILE=/var/lib/zt/issuance.halt PYTHONPATH=src python -m layer6_soar.killswitch --level 1
```

## 知っておく限界

- **記録の「末尾の切り落とし」は、このファイルの中だけでは分からない。** 鎖の先頭 (件数とハッシュ) を別の場所へ控えて、
  検算のときに渡す必要が在る。控える仕組みはまだ無い (手で控える)。
- **国と回線は見ていない。** IP から国・回線を引く仕組みが無いので、「いつもと違う国」の規則は今は働かない。
- **送信元の IP は、つないできた相手の IP をそのまま使う。** 前にプロキシを置くなら、プロキシが渡す IP を信用する設定が要る (まだ無い)。
- **セッションと出来事はメモリの中。** 再起動で消える。複数台では共有されない。
- **知らせ (通知) はメモリに溜めるだけ。** 送り先 (Webhook ほか) が決まってから足す。
- **nftables のルールは、本物のサーバーでまだ試していない。**
- **第 3 層は、実物の物理キーとスマホでまだ試していない。** 検査はソフトで作った認証器で、画面はブラウザ (Chromium) の試験用の認証器で通している。
- **画面のブラウザでの通しは、`zero-trust-gateway/` を触ったときだけ CI で回る** (`gateway-browser.yml`)。ほかの変更では走らない。
  Chromium の試験用の物理キーは登録のたびに新しい自作の証明書を作るので、物理キーの**登録が通る形**はブラウザで試せない (入口は「知らない発行元」として正しく断る)。
  ブラウザの検査は、登録済みの物理キーを用意して確認を通し、物理キーの登録は「断られる」側だけを通す。
- **画面は `PUBLIC_BASE_URL` の下の `/auth/` で、https で開く。** 別の名前で開くと、DPoP の証明の宛先と WebAuthn のオリジンが合わずに断られる。
- **画面が受け付ける署名の方式は ES256 と EdDSA だけ。** Chrome は「RS256 が無い」と警告を出す。RS256 しか使えない古い認証器は登録できない。
- **スマホのパスキーは、機種の証明を取らない** (同期されるパスキーは証明を出さないため)。登録のときの端末は信用する前提になる ——
  登録コードを渡す道と、登録の知らせ (「認証器を登録しました」) で補う。
- **同期されないスマホの鍵は登録できない。** 物理キーと取り違えないための線引きなので、そういう設定のスマホは使えない。
- **登録コードは、切れるまで (15 分) の間は持っている人が使える。** 渡す道を選ぶ。使えるのは、その人がまだ持っていない種類の登録だけ。
- **乱数の控えと認証の状態はメモリの中。** 再起動すると、確認はやり直し (登録した認証器はファイルに残る)。控えには天井が在り、
  満杯の間は新しい確認を始められない —— 入口での回数の制限 (前に置くプロキシ・第 1 層) が要る。
- **認証器の控えのファイルは、1 つのプロセスが書く前提。** 複数台・複数プロセスで同じファイルを書くと、後から書いた方が勝つ。
- 「絶対に破られない」とは言えない。層を重ねて、1 つ破られても次で止まる・気付ける形を目指している。
